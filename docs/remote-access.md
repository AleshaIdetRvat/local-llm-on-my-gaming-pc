# Управление ПК по сети (`RIG_MODE=ssh`)

> **Нужно только если агент живёт не на самом ПК с видеокартой.**
> Если ты запускаешь агента прямо на этом Windows-ПК (`RIG_MODE=local`) — пропусти
> весь файл: ни SSH, ни правил файрвола, ни возни с VPN тебе не понадобится.
> Общие для обоих режимов грабли — в [windows-notes.md](windows-notes.md).

Схема: на ПК поднят OpenSSH Server, агент с другой машины выполняет на нём
PowerShell-команды и забирает файлы. API llama-swap при этом слушает всю локальную сеть,
а не только localhost.

```bash
ssh -i $RIG_SSH_KEY -o BatchMode=yes $RIG_SSH_USER@$RIG_HOST '<powershell-команда>'
```

Значения подставляются из `rig.local.env`. Дефолтный шелл OpenSSH на Windows — PowerShell,
так что кавычить нужно по правилам PowerShell, а не bash.

## Настройка доступа

- **Заведи отдельного ASCII-юзера-администратора** под SSH (почему — см.
  [windows-notes.md](windows-notes.md#кириллическое-имя-пользователя)).
- **Публичный ключ администратора кладётся не туда, куда обычно.** Для юзеров из группы
  «Администраторы» OpenSSH на Windows читает не `~/.ssh/authorized_keys`, а общий файл
  `C:\ProgramData\ssh\administrators_authorized_keys`.
- **⚠️ И он игнорируется, если у файла слишком широкие права.** Доступ надо срезать до
  Administrators + SYSTEM, причём через **SID**, а не имена групп:

  ```powershell
  icacls C:\ProgramData\ssh\administrators_authorized_keys /inheritance:r `
         /grant '*S-1-5-32-544:F' /grant '*S-1-5-18:F'
  ```

  Симптом при неправильных правах — сервер молча не принимает ключ и просит пароль,
  никакой внятной ошибки клиенту не приходит.

## VPN-ловушка — самая частая причина «всё сломалось»

**AmneziaVPN, Outline и подобные забирают домашнюю подсеть в туннель, и SSH к ПК
перестаёт проходить — таймаут на порт 22.**

Со стороны это выглядит как сдохший ПК: SSH не идёт, API не отвечает. При этом сам ПК
работает нормально, и с его экрана всё в порядке.

**Если SSH внезапно таймаутит — первым делом проверь, не включён ли VPN на ПК**,
и попроси выключить. Лечится по-настоящему настройкой split-tunnel — исключением
домашней подсети в настройках VPN-клиента.

## ⚠️ Профиль сети сам сбрасывается в Public

Windows время от времени переключает Wi-Fi-сеть обратно в **Public**, и файрвол начинает
резать порт 22. Симптом ровно тот же, что у VPN-ловушки: `Operation timed out`.
Если VPN выключен, а SSH всё равно не идёт — смотри профиль сети:

```powershell
Get-NetConnectionProfile
Set-NetConnectionProfile -Name '<SSID>' -NetworkCategory Private
```

**Ping тут не помощник:** Windows по умолчанию не отвечает на ICMP, так что молчащий
ping — норма и ни о чём не говорит.

## Файрвол

- Домашняя сеть должна быть в профиле **Private**.
- Правила: `sshd` на 22 (Any), `llama-server` на 8080 (Private).
- Наружу не пробрасывается ничего: и API, и SSH живут только внутри домашней подсети.
  API llama-swap не имеет аутентификации в привычном смысле (ключ — любая непустая строка),
  поэтому выставлять его в интернет нельзя.

## Забирать файлы — только scp

`Get-Content` через SSH ломает UTF-8 и портит бинарники. Для любых файлов:

```bash
scp -i $RIG_SSH_KEY $RIG_SSH_USER@$RIG_HOST:C:/путь/файл .
```

Это же правило действует, когда синхронизируешь зеркала конфигов с ПК обратно в репо.

## Detached-процессы умирают вместе с SSH-сессией

OpenSSH на Windows кладёт всё порождённое сессией в один job-объект и убивает его при
отключении. **`Start-Process` от этого не спасает** — фоновый процесс умрёт вместе с сессией.

Кусается это в двух местах: долгие скачивания весов и запуск самого сервера.

Что работает:

- держать процесс **в форграунде SSH**, а фоновость обеспечивать на стороне агента
  (запустить саму ssh-команду в фоне);
- либо порождать процесс мимо job-объекта:

  ```powershell
  Invoke-CimMethod -ClassName Win32_Process -MethodName Create -Arguments @{CommandLine='...'}
  ```

  Так запущенный процесс переживает отключение SSH.

## GPU из session 0

SSH-сессия на Windows — это session 0, и по общему правилу WDDM CUDA там недоступна.
На нашем стенде это оказалось неправдой: CUDA из session 0 работает на полной скорости.
Проверить у себя стоит до того, как строить планы вокруг этого ограничения —
подробности в [windows-notes.md](windows-notes.md#gpu-из-session-0).
