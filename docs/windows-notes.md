# Грабли Windows

Всё, что кусало нас на пути, независимо от того, сидишь ты за самим ПК
(`RIG_MODE=local`) или ходишь на него по сети (`RIG_MODE=ssh`).
Чисто сетевые проблемы вынесены отдельно — [remote-access.md](remote-access.md).

## Fast Startup ломает автозапуск

Главная засада с автозапуском, и распознать её тяжело: сервер после включения ПК не встаёт,
хотя задача в планировщике настроена правильно и вручную запускается.

Причина: на Windows 11 по умолчанию включён Fast Startup (`HiberbootEnabled=1`).
Обычное «Завершение работы → включение» — это **резюм из гибернации ядра, а не настоящий boot**,
поэтому триггер «At Startup» не срабатывает. Он сработает только после честного Restart.

Проверить:

```powershell
Get-ItemProperty 'HKLM:\SYSTEM\CurrentControlSet\Control\Session Manager\Power' HiberbootEnabled
```

Лечится двумя способами. Отключить Fast Startup — но тогда ПК дольше включается,
а он всё-таки игровой. Мы выбрали второй: **два триггера у задачи** — At Startup (для настоящего
Restart) и At Logon (для обычного включения, потому что после включения юзер всё равно логинится).
От двойного запуска защищает `MultipleInstancesPolicy=IgnoreNew`.

## Планировщик задач

Сервер держим задачей планировщика, а не службой: службе пришлось бы объяснять про GPU
и про то, как её перезапускать, а задача умеет и автостарт, и рестарт при падении,
и запуск от нужного юзера.

- Задача, созданная как **S4U** (запуск от юзера без сохранённого пароля), меняется через
  `Set-ScheduledTask` **без пароля**. А вот `schtasks /Change` пароль потребует — используй
  PowerShell-командлеты, а не `schtasks`, когда правишь задачу.
- Управление: `schtasks /Run /TN <имя>` и `schtasks /End /TN <имя>`.
- Смена команды запуска: `New-ScheduledTaskAction` + `Set-ScheduledTask`.

## Локализованная (русская) Windows

⚠️ Встроенные группы называются по-русски: «Администраторы», «Пользователи». Поэтому
`icacls ... /grant Administrators:F` и `Add-LocalGroupMember -Group Administrators`
падают с «нет такой группы».

**Всегда обращайся к встроенным группам по SID**, а не по имени:

| SID | Группа |
|---|---|
| `*S-1-5-32-544` | Администраторы |
| `*S-1-5-18` | SYSTEM |
| `*S-1-5-32-545` | Пользователи |

Это касается и `icacls`, и `Add-LocalGroupMember`, и `New-ScheduledTaskPrincipal`.

## Кириллическое имя пользователя

Windows делает имя пользователя из имени владельца, и на русской системе оно оказывается
кириллическим — вместе с путём `C:\Users\<кириллица>`. Это ломает кодировку в SSH-сессии
и периодически всплывает в сторонних утилитах.

Заводить отдельную **ASCII-учётку-администратора** под LLM-хозяйство — дешевле, чем чинить
кодировки поштучно. Даже в local-режиме это полезно: пути установки не будут содержать кириллицы.

## Скачивание больших файлов (веса моделей)

Веса — это десятки гигабайт одним файлом, и на середине всё обрывается.

- **`curl.exe` есть в Windows из коробки** и качает быстро (у нас 13–34 МБ/с). Python/pip
  для скачивания не нужен — не тащи `huggingface-cli` только ради загрузки.
- **Резюм обязателен:** `curl -C -` плюс `--speed-limit` / `--speed-time`. Без них зависшее,
  но формально живое TCP-соединение не считается ошибкой, и `--retry` его не ловит —
  скачивание встаёт намертво, а ты этого не видишь.
- **Проверяй размер байт в байт** с тем, что отдаёт HF API. Оборванный GGUF грузится
  и падает уже в llama.cpp с невнятной ошибкой.
- Если качаешь по SSH — читай про job-объект в [remote-access.md](remote-access.md),
  иначе процесс умрёт вместе с сессией.

## Мониторинг

- **VRAM:** `nvidia-smi --query-gpu=memory.used --format=csv,noheader,nounits`.
  Мерить **во время генерации**. В простое WDDM вытесняет память процесса в RAM,
  и цифра получается неправдоподобно низкой — это не баг и не выгрузка модели.
- **Логи:** llama-swap и llama-server пишут в файлы; клади их в путь, доступный из любой
  сессии (мы используем `C:\Users\Public\`), иначе из-под другого юзера их не прочитать.
- **Живость API:** `curl <RIG_API>/models`.

## GPU из session 0

Общее правило гласит, что под WDDM в сессии 0 (службы, задачи планировщика, SSH-сессии)
CUDA недоступна. **На практике это не всегда так** — на нашем стенде llama-server
из session 0 прекрасно видит GPU и выдаёт полную скорость.

Вывод простой: не отказывайся от автозапуска задачей из-за этого правила — сначала проверь.
Проверка: `nvidia-smi` в той сессии, где будет жить сервер.
