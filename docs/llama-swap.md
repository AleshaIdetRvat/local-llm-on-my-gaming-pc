# llama-swap: несколько моделей на одной видеокарте

## Зачем он нужен

В 16 ГБ VRAM помещается ровно одна приличная модель. Но нужны разные: быстрая для
простых задач, длинноконтекстная для больших файлов, ещё одна с vision. Держать их
одновременно нельзя, а перезапускать `llama-server` руками каждый раз — мучение.

[llama-swap](https://github.com/mostlygeek/llama-swap) решает это: он слушает один порт,
раздаёт OpenAI-совместимый API и **по полю `model` в запросе сам поднимает нужный
`llama-server`, а предыдущий глушит**. Клиент просто пишет другое значение `model`
и получает другую модель; адрес и ключ не меняются.

Оверхеда прокси не добавляет — [замеряли](../rigs/rtx5070ti-16gb/benchmarks.md#llama-swap-оверхеда-нет-2026-07-08),
разница в пределах шума.

Цена — пауза на переключение: выгрузить старую модель и загрузить новую занимает
секунды-десятки секунд (зависит от размера весов и скорости диска).

## Конфиг

Один YAML. Шаблон с комментариями — [`templates/config.yaml`](../templates/config.yaml),
живой пример на 7 моделей — [`rigs/rtx5070ti-16gb/pc-mirrors/config.yaml`](../rigs/rtx5070ti-16gb/pc-mirrors/config.yaml).

Скелет:

```yaml
healthCheckTimeout: 300     # сколько ждать готовности модели, сек
globalTTL: 1800             # выгрузить модель из VRAM после N сек простоя
logLevel: info

macros:
  server: >                 # общие флаги для всех моделей — чтобы не повторять
    C:\llm\llama.cpp\llama-server.exe
    --port ${PORT}
    -ngl 999 -np 1 -fa on
    --cache-type-k q8_0 --cache-type-v q8_0
    -t 6 -b 2048 --jinja

models:
  моя-модель:
    cmd: |
      ${server}
      -m C:\llm\models\моя-модель\weights.gguf
      -c 32768 -ub 512
    aliases:
      - default
```

Что здесь важно:

- **`${PORT}`** llama-swap подставляет сам — каждый `llama-server` поднимается на своём
  внутреннем порту, наружу торчит только порт прокси.
- **`healthCheckTimeout`** должен быть с запасом больше времени загрузки самой тяжёлой
  модели. Иначе прокси решит, что модель не поднялась, ровно в тот момент, когда она
  честно грузит 20 ГБ с диска.
- **`globalTTL`** — выгрузка по простою. Для игрового ПК это ключевая настройка:
  через полчаса безделья VRAM освобождается сама, и игра запускается без плясок.
  Следующий запрос перегрузит модель. Поставь `0`, если хочешь, чтобы модель висела всегда.
- **`aliases`** — стабильное имя для клиентов. Заведи `default` и повесь его на текущую
  прод-модель: когда поменяешь модель, достаточно перевесить алиас в конфиге,
  а клиентов трогать не придётся.
- **`macros`** — общие флаги. Модель, которой нужен другой бинарник (например форк
  llama.cpp), макрос не использует и прописывает команду целиком.

## Три тонкости, на которых легко застрять

**1. llama-swap не снимает кавычки в `cmd:`.** Из-за этого любой флаг со значением-JSON
ломается — например `--chat-template-kwargs '{"enable_thinking":true}'` приедет в
llama-server вместе с кавычками и не распарсится. Передавай такие вещи через `env`:

```yaml
  моя-модель:
    env:
      - 'LLAMA_ARG_CHAT_TEMPLATE_KWARGS={"enable_thinking":true}'
    cmd: |
      ${server}
      ...
```

Почти у каждого флага llama-server есть парный `LLAMA_ARG_*`.

**2. Нативные эндпоинты llama-server живут под `/upstream/`.** `/completion`, `/props`,
`/slots`, `/apply-template` через обычный путь отдадут 404: в нативном API нет поля `model`,
и прокси не знает, кому маршрутизировать. Правильный адрес:

```
http://<host>:8080/upstream/<model_id>/completion
```

Это же используют бенч-скрипты — им нужен именно нативный `/completion`, чтобы получить
честные тайминги prefill и decode.

**3. `--watch-config` перечитывает конфиг сам.** Правки `models:` подхватываются без
рестарта — меняй и сразу проверяй. Рестарт нужен, только если поменял флаги самого
llama-swap (порт, путь к конфигу).

## Запуск и автозапуск

Запускается одной строкой:

```bat
llama-swap.exe --config <путь>\config.yaml --listen 0.0.0.0:8080 --watch-config > <лог> 2>&1
```

- `--listen 0.0.0.0:8080` — слушать всю локальную сеть. Нужно, если агент или клиенты
  ходят с других машин. Для чисто локального сценария достаточно `127.0.0.1:8080`,
  и тогда не придётся трогать файрвол.
- Лог клади туда, куда пускают из любой сессии (`C:\Users\Public\`) — иначе не прочитаешь
  его из-под другого юзера.

Автозапуск делаем **задачей планировщика** (готовый рецепт и обязательные грабли —
[windows-notes.md](windows-notes.md#fast-startup-ломает-автозапуск); коротко: нужны
**два** триггера, At Startup и At Logon, иначе Fast Startup оставит тебя без сервера).

Управление задачей:

```powershell
schtasks /Run /TN llama-server     # поднять
schtasks /End /TN llama-server     # погасить
taskkill /IM llama-swap.exe /F     # добить процесс при полном рестарте
```

## Проверка, что всё живо

```bash
curl <RIG_API>/models              # список моделей и алиасов
```

Плюс веб-дашборд на `http://<host>:8080/ui` — видно, какая модель поднята сейчас,
и логи по каждой.

## Как добавить модель

1. Скачать GGUF (грабли скачивания — [windows-notes.md](windows-notes.md#скачивание-больших-файлов-веса-моделей)).
2. Дописать блок в `models:` — обычно это `${server}`, `-m <путь>`, `-c <контекст>`
   и сэмплинг, рекомендованный авторами модели.
3. Сохранить конфиг — `--watch-config` подхватит сам.
4. `curl <RIG_API>/models` — убедиться, что модель появилась.
5. Прогнать [замер](benchmarks.md) и записать цифры в свой `rigs/<стенд>/benchmarks.md`.

Подбор `-c`, `-ub` и `--n-cpu-moe` под свою видеокарту — [choosing-models.md](choosing-models.md).
