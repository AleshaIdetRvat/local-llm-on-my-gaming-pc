# План: Qwen3.6-35B-A3B на RTX 5070 Ti → OpenAI-API в локальной сети

> Цель: на игровом ПК (Windows 11) поднять `Qwen3.6-35B-A3B` через **llama.cpp `llama-server`**,
> раздать **OpenAI-совместимый `/v1` API в локальную сеть**, обращаться к нему с макбука.
> Основной сценарий: **код + чат, один пользователь**, упор на качество (Q4) при разумной скорости.

### Почему MoE 35B-A3B (а не плотная 27B)
- Хороший Q4-квант 35B ≈ 22 ГБ — целиком в 16 ГБ не влезет, но **MoE спокойно переносит потолок VRAM**: эксперты уходят в RAM, а на токен реально считается только ~3B активных → штраф за оффлоад умеренный.
- Держим **полное Q4-качество**. Плотную 27B пришлось бы жать в Q3/IQ4_XS, чтобы влезла в VRAM, — для кода это нежелательная потеря точности.
- Цена: упор в DDR5-5600 / 6 ядер 7400F при счёте выгруженных экспертов; 32 ГБ RAM — впритык.

### Архитектура Qwen3.6-35B-A3B: гибрид MoE + linear attention — что это значит для KV-кэша
Подтверждено по карточке HF, GitHub `QwenLM/Qwen3.6` и независимому разбору KV-кэша (модель свежая, июнь-2026, вне базы знаний модели — сверено живым поиском):
- MoE-слой: 256 «routed» экспертов + 1 always-on shared, top-8 роутинг → реально считается **9 экспертных модулей на токен** (отсюда A3B).
- 40 слоёв = 10 повторов блока [3× (Gated DeltaNet → MoE) → 1× (Gated Attention → MoE)] → **30 из 40 слоёв — Gated DeltaNet** (линейное внимание/delta-rule, родственно Mamba2 SSD; в видео-источниках это неточно названо «SSM»), **10 из 40 — обычное full attention**.
- ⚠️ Важно для бюджета KV: **только 10 attention-слоёв** держат обычный, растущий с контекстом KV-кэш; 30 DeltaNet-слоёв держат рекуррентное состояние **фиксированного размера**, не растущее с контекстом. Независимая оценка по attention-слоям (2 KV-головы, head_dim 256, fp16): ~20.5 КБ/токен.
- Практический вывод: апгрейд контекста (64K/128K, native-лимит модели — 256K, расширяемо через YaRN) почти не бьёт по VRAM по сравнению с классической all-attention моделью такого размера — упор скорее в качество работы с длинным контекстом, а не в память.
- **Пересчёт под наш контекст ~100K (102400):** 20.5 КБ/токен (fp16) × 102400 ≈ 2.05 ГБ; в `q8_0` (вдвое легче fp16) — **≈ 1.0–1.1 ГБ** на 10 attention-слоёв при batch=1. Для сравнения на 32K было бы ≈ 0.33–0.34 ГБ в q8_0 — рост контекста втрое почти втрое поднимает и KV-бюджет, но абсолютная цифра (~1 ГБ) всё равно умеренная на фоне 16 ГБ VRAM. Это прикидка по независимому разбору архитектуры, не измерение — **сверить по факту через `nvidia-smi` при первом запуске** с `-c 102400` и учесть при подборе `--n-cpu-moe` в Фазе 4.

## ФАЗА 4 — Запуск + тюнинг MoE-оффлоада (🤖 АГЕНТ, 20–40 мин)
1. **Стартовый запуск** (консервативный, чтобы точно загрузился):
   ```powershell
   C:\llm\llama.cpp\llama-server.exe `
     -m C:\llm\models\qwen36-35b\Qwen3.6-35B-A3B-UD-Q4_K_XL.gguf `
     --host 0.0.0.0 --port 8080 `
     -ngl 999 --n-cpu-moe 30 `
     -c 102400 -fa on `
     --cache-type-k q8_0 --cache-type-v q8_0 `
     -t 6 -b 2048 -ub 512 `
     --jinja
   ```
   - `-c 102400` — контекст ~100K, как и нужно для рабочего сценария (не 32K, см. пересчёт KV-бюджета выше: ~1.0–1.1 ГБ VRAM на KV в q8_0).
   - Без `--spec-type draft-mtp` — **первая итерация без MTP**, чисто как обычная модель. MTP пробуем отдельно в Фазе 7, когда базовый запуск уже стабилен.
   - `-ngl 999` — все слои на GPU, но `--n-cpu-moe N` возвращает **эксперт-тензоры первых N слоёв** в RAM.
   - **Смысл тюнинга:** меньше `N` → больше экспертов на GPU → **быстрее**, но больше VRAM. Ищем **минимальный N, при котором всё ещё влезает**.
2. **Тюнинг-петля (делаю я):** смотрю `nvidia-smi` (VRAM), снижаю `--n-cpu-moe` (30 → 28 → 26…), пока занятая VRAM не подойдёт к **~15 ГБ** (запас ~1 ГБ). Самое низкое N, что грузится без OOM — рабочее. Учитываю, что на 100K контексте KV сам по себе занимает заметно больше VRAM, чем на 32K (~1 ГБ против ~0.33 ГБ) — это часть бюджета, не сверх него.
3. **Доп. флаги для тонкой настройки** (пробовать после первого успешного запуска, не в стартовый консервативный конфиг; источник идей — два видео про llama.cpp, флаги сверены по апстрим-репозиторию и `--help`):

   | Флаг | Что даёт | Когда включать | ⚠️ |
   |---|---|---|---|
   | `--no-mmap` | Грузит весь GGUF в RAM одним блоком вместо ленивого mmap — убирает page-fault-стопоры при декоде CPU-офлоаженных экспертов (анекдотически до +30% decode в одном видео, официального бенчмарка апстрим не публиковал) | Только если есть подтверждённый запас RAM | **Известное открытое ограничение апстрима (issue #9059): при `--no-mmap` в RAM грузится ВЕСЬ файл (22.85 ГБ), включая GPU-слои, и эта память не освобождается после копирования в VRAM.** 22.85 ГБ файла + ~6–8 ГБ Windows ≈ 29–31 ГБ из наших 32 ГБ (~22 ГБ free по префлайту) — реальный риск OOM/свопа на старте. Не включать по умолчанию, тестировать отдельно с закрытыми Chrome/играми. |
   | `--mlock` | Блокирует страницы модели от свопа (на Windows — через WinAPI `VirtualLock`) | Если без `--no-mmap` всё равно видны просадки от свопа после долгого аптайма | На Windows **не требует похода в `secpol.msc`** за `SeLockMemoryPrivilege` — это непроверенное утверждение из одного из видео-источников, апстрим-код этого не делает: при неудаче `VirtualLock` llama.cpp сама ретраит через увеличение working set процесса. Идти в `secpol.msc` имеет смысл только если в логе реально `failed to VirtualLock`. |
   | ~~`--cache-reuse 256`~~ → `--ctx-checkpoints 8 --checkpoint-min-step 1024` | `--cache-reuse` (KV-shift) на нашей recurrent-модели **не работает** (`cache_reuse is not supported by this context`) — убран. Реюз префикса даёт **context checkpoints** (снимок рекуррентного состояния). | Уже в конфиге; тюнить под агента в Фазе 4/7 | Дефолтный `--checkpoint-min-step 8192` бесполезен на ходах < 8К → снизили до 1024. Даёт почти полный реюз растущей истории (reprocess 4 vs ~2048 токена), но смена system-промпта = reprocess от ближайшего checkpoint. См. развёрнуто в статус-блоке выше (находка 2026-07-01). |
   | `-t 6` | Явно фиксирует число CPU-тредов под офлоаженные эксперты (вместо `-1`/auto) | Сразу — на 7400F (6c/12t) лучше зафиксировать физические ядра, чем доверять авто-детекту | — |
   | `-ub` (ubatch, дефолт 512) | Размер физического батча на prefill — больше → быстрее prefill (особенно в bandwidth-bound MoE-офлоаде), но больше пиковой RAM/VRAM при обработке промпта | Поднимать (1024/2048) в Фазе 7 по результатам бенчмарка | На наших 32 ГБ RAM поднимать осторожно, после замера. |

   Все флаги не зависят от версии CUDA/билда — generic CLI-опции, должны быть видны в `llama-server.exe --help`.
4. **Заметки по модели:** «думающая» (`<think>` вкл. по умолчанию) — для кода часто полезно, но добавляет задержку; при желании отключу через шаблон/параметры запроса. Сэмплинг под Qwen: temp 0.6 / top_p 0.95 / top_k 20.

## ФАЗА 7 — Бенчмарк и докрутка (🤖 АГЕНТ, по желанию)
0. **PP (prefill) важнее TG (decode) для кодового агента.** Агентские сценарии (Cursor/Continue/Claude Code через `/v1`) шлют длинные промпты (контекст файлов, system-промпт, история тулзов) и просят сравнительно короткие ответы → ощутимая доля времени уходит в **prefill**, а не в decode, особенно на первом запросе без cache-reuse. Бенчить и тюнить нужно отдельно pp и tg, не только decode tok/s:
   ```powershell
   llama-bench.exe -m C:\llm\models\qwen36-35b\Qwen3.6-35B-A3B-UD-Q4_K_XL.gguf `
     -p 512,4096,16384 -n 128 -ub 256,512,1024,2048 --n-cpu-moe 30
   ```
   (если конкретная сборка `llama-bench` не подхватывает `--n-cpu-moe` в свипе — гонять `llama-server` напрямую и мерить вручную через `timings` в ответе `/v1/chat/completions`). Поднятие `-ub` обычно ускоряет pp ценой пиковой памяти при обработке промпта (проверено: ub 2048 → ~2830 pp); в связке с context checkpoints (`--checkpoint-min-step 1024`, Фаза 4) повторный prefill на совпадающем растущем префиксе резко проседает — **уже подтверждено** (reprocess 4 vs ~2048 токена).
1. `llama-bench` на модели: фиксирую **prefill (pp)** и **decode (tg)** tok/s при разных `--n-cpu-moe` → выбираю оптимум.
2. Рычаги, если мало скорости/памяти: ↓`--n-cpu-moe` (если есть запас VRAM); ↓контекст; KV в q4_0; попробовать форк **`ik_llama.cpp`** (заточен под гибрид CPU/GPU MoE, может дать +10–20%).
3. **Тест MTP (Multi-Token Prediction).** ✅ **ПРОВЕРЕНО НА ФАКТЕ 2026-07-01 — замеры в `mtp-experiment-2026-07-01/RESULTS.md`.** Итог: MTP-голова в нашем GGUF **есть и активируется** (в `timings` живьём `draft_n`/`draft_n_accepted` — оба риска ниже сняты). Но **дефолтный `--spec-draft-n-max 3` = −34% декода** (verify-батч тянет union экспертов из RAM, растёт с окном), `n-max 2` = −4%, а **`--spec-draft-n-max 1` = +11%** над baseline (73.6 → ~81.5 t/s, acceptance ~88%). VRAM с MTP 15803 MiB (запас ужимается 790→500 MiB), понизить `n-cpu-moe` нельзя — уже у потолка. **Решение: прод оставлен на baseline без MTP** (по договорённости); `n-max 1` — задокументированный опциональный +11% одной строкой, если захочется вернуться. Ниже — исходные заметки (актуальны, но переигрывать `n-max` под наш оффлоад: не 2, а **1**):
   - Два разных механизма, не путать:
   - **Классический spec decoding с отдельной drafter-моделью (`-md`) — подтверждённо НЕ работает на этой модели.** Независимые бенчи (19 конфигураций на RTX 3090, llama.cpp discussion #22473) показывают замедление: батч из draft-токенов на MoE требует подгрузки union экспертов сразу по нескольким позициям (до ~64 вместо одного набора на verify-проход), что съедает выигрыш даже при высоком acceptance rate. **Не пробовать `-md`/внешний drafter здесь.**
   - **MTP (своя голова модели, не внешняя модель) — другая история, заметно более многообещающая.** В PR ggml-org/llama.cpp#22673 (слит в mainline 16.05.2026) автор репортит ~75% acceptance / >2× ускорение на Qwen3.6-27B/35B-A3B; независимые репорты в той же ветке на близких по духу конфигурациях (CPU/RAM-bound офлоад) показывают реальный прирост — вплоть до +28% на связке 6 ГБ VRAM + 64 ГБ RAM. Команда (как и было в плане): `-np 1 --spec-type draft-mtp --spec-draft-n-max 2`.
   - ⚠️ Два риска проверить по факту, не считать данностью:
     1. **MTP-голова должна реально быть в GGUF.** По независимым репортам обычный квант без MTP-сборки голову может не содержать — сверить, что наш `unsloth/Qwen3.6-35B-A3B-MTP-GGUF` действительно тащит MTP-тензор (запасной вариант — `ggml-org/Qwen3.6-35B-A3B-MTP-GGUF`).
     2. **Фича может молча не активироваться** без ошибки в выводе на части GPU/билдов (известный баг на старых архитектурах, issue #24670) — смотреть в логе сервера строку про `draft-mtp`/acceptance rate, не верить на слово, что флаг сработал.
   - Билд llama.cpp — строго **после 16.05.2026** (PR #22673), CUDA-путь (наш случай, RTX 5070 Ti Blackwell) — наиболее обкатанный backend для этой фичи. Комбинация `--spec-type draft-mtp` + `--n-cpu-moe` подтверждена сторонним issue на похожем железе — сочетать с нашим оффлоадом можно.

## Приложение — идеи на будущее (проверены, в текущий план не идут)

**TurboQuant (KV-сжатие, флаги `-ctk turbo4 -ctv turbo3` / `tbq3_0`/`tbq4_0`) — пока не трогаем.** Техника реальна (Google Research, статья arXiv:2504.19874, доклад на ICLR 2026), но в mainline llama.cpp её нет: исходный PR закрыт мейнтейнером без мерджа (02.06.2026, «нет доказательств, что оправдывает opportunity cost»), потому что ggerganov уже смержил более простой fix — поворот активаций перед существующими типами квантования (PR #21038), без новых типов и без форка. То есть наш текущий выбор `--cache-type-k q8_0 --cache-type-v q8_0` уже частично получает этот бонус бесплатно на свежем билде.
> **Повторно перепроверено 2026-07-01** (после вопроса про скриншот с `-ctk turbo4 -ctv turbo3`): статус не изменился. Ещё один заход на мердж — PR `#23962 "Merge turboquant"` (закрыт 2026-06-01) — снова закрыт **без мерджа** (`merged: false`, сверено напрямую через GitHub API). Всего за последние месяцы в `ggml-org/llama.cpp` было ~25 PR/issue с TurboQuant, почти все закрыты, часть — с пометкой «AI policy violation» (волна низкокачественных авто-сгенерированных PR). Live-проверка исходников ветки `master` (`enum ggml_type` в `ggml/include/ggml.h`) подтверждает: типов `TBQ3_0`/`TBQ4_0`/turbo там нет. Флаги `turbo3`/`turbo4` со скриншотов работают только в сторонних форках (`TheTom/llama-cpp-turboquant`, `AtomicBot-ai/atomic-llama-cpp-turboquant` — этот форк, кстати, прицельно заточен под Qwen 3.6 + MTP/NextN speculative decoding, и другие, расплодившиеся за пару дней после анонса), а не в официальных пребилтах, которые мы качаем в Фазе 3. Это нестабильный сторонний код без CI, CUDA-путь не обкатан на Blackwell/RTX 50-серии, а независимое тестирование на 3-бит показало реальную (не «lossless», вопреки маркетингу) просадку качества. Риск не оправдан — пропускаем.

**REAP-прунинг (Cerebras, arXiv:2510.13999) — два разных варианта, разный вердикт:**

| Вариант | Статус | Вывод |
|---|---|---|
| `unsloth/GLM-4.7-Flash-REAP-23B-A3B-GGUF` (официальный Cerebras-прун + Unsloth-квант, **другая модель**, не Qwen3.6) | Подтверждён, near-lossless (HumanEval 94.5→95.1 — разница в пределах шума, не «улучшение») | UD-Q4_K_XL — **14.2 ГБ, целиком влезает в 16 ГБ VRAM без CPU-офлоада вообще.** Опциональный сайд-квест, если захочется сравнить скорость/качество без MoE-офлоада на CPU. Квант ~17.3 ГБ против наших 22.85 ГБ — потенциально меньше офлоада, но тестировать только бок-о-бок с текущим Q4_K_XL, не доверять на слово. |
